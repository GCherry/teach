Lesson 0002 · Zone of Proximal Development: Cons, Security & Decision Judgment

The Hidden Costs of MCP (And When to Use a REST API or CLI)

Your instinct in LR-0001—that MCP can feel like heavy ceremony around an API—is often right. Every protocol capability you saw in Lesson 0001 carries a measurable engineering cost inside GCherry/ytmix.

1. Five Concrete Cons Grounded in ytmix/internal/mcp/

Con 1 · Upfront Context-Window Tax

When an MCP Host connects to ytmix mcp, tools/list sends all 9 tool descriptions and JSON Schemas into the model's prompt before the user writes a word. Connect five or ten servers and thousands of schema tokens burn context budget, degrade tool selection accuracy, and slow time-to-first-token (Anthropic — Code Execution with MCP). Intermediate JSON payloads (like inspect_tracks returning every .mp3 Track object) also pass through the model's context on every turn.

Con 2 · Stateful Subprocess Lifecycle & Stdout Fragility

An HTTP endpoint is stateless per request. By contrast, server.go runs a long-lived local process wired to stdin/stdout with a 16 MiB line cap. Any accidental fmt.Println to stdout from a dependency corrupts JSON-RPC framing for the entire session (ytmix explicitly redirects all diagnostics to ErrOut / stderr). Stdio servers also couple directly to the local machine's binaries (ffmpeg, ffprobe) and filesystem paths.

Con 3 · Long-Running Async Work & Binary Payloads

Compare rendering in ytmix ui vs. ytmix mcp:

  • ytmix ui: Opens GET /api/render/{id}/events (Server-Sent Events) and pushes real-time FFmpeg progress straight to the browser, then streams .mp4 bytes via GET /api/render/{id}/output.
  • ytmix mcp: start_render launches a goroutine and returns a jobId, forcing the LLM to burn inference turns polling get_render_status or reading ytmix://jobs/{id}—and it cannot cleanly stream gigabyte video binaries over stdio JSON.

Con 4 · Non-Deterministic Callers & Prompt Injection Surface

Software calling a REST API never gets tricked by data it reads. An LLM calling inspect_tracks reads untrusted rawId3Title metadata straight from downloaded .mp3 files into its context window—a classic indirect prompt injection vector. Meanwhile, ToolAnnotations (readOnlyHint, destructiveHint) are advisory hints only; malicious or buggy Hosts can ignore them, so ytmix still enforces strict decoding (DecodeToolArgs with DisallowUnknownFields()) and refuses to mutate source .mp3 files.

Con 5 · Extra Maintenance Surface Over a CLI

If your caller is already a coding agent with bash access (like Antigravity or Claude Code), maintaining a separate MCP layer duplicates flag parsing, schema definitions, and tests—when the agent could run ytmix --help and invoke the CLI directly with zero idle schema tokens.

Figure 1: Choose MCP when runtime cross-Host discovery, consent hints, or Prompts solve an M×N problem—not as a reflex wrapper around every internal API.

Reference 0002 · Quick Lookup

5-gate decision rule & top MCP failure modes.

  • Use HTTP REST/SSE for deterministic software callers or browser UIs (ytmix ui).
  • Use CLI when a coding agent already has shell access and you want zero idle schema tokens.
  • Use MCP when multiple AI Hosts need runtime discovery, consent hints, URI Resources, and curated Prompts.
