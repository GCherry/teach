Lesson 0001 · Zone of Proximal Development: Protocol Boundaries & Primitives

Why MCP Is Not Just Another API (Using ytmix)

Look at GCherry/ytmix: one Go audio-mix engine exposed three ways—a CLI, an HTTP REST+SSE server (ytmix ui), and a stdio MCP server (ytmix mcp). If both ytmix ui and ytmix mcp accept JSON and trigger renders, why does MCP exist at all?

Core Mental Shift

A REST API is designed for deterministic software written at build time by a human programmer who read your docs. MCP (2025-06-18 Spec) is a runtime discovery and control contract for a non-deterministic LLM Host that had never seen ytmix until this session started.

1. One Engine, Three Callers in ytmix

In MISSION.md, the goal is architectural judgment. The cleanest way to see where MCP diverges from an API is to compare how three callers drive the exact same internal/mixer pipeline in ytmix:

  • ytmix CLI: Written for a human shell (or a bash-capable agent). Discovery happens via --help; input is positional flags; output is human stdout text plus exit codes.
  • ytmix ui (HTTP REST + SSE): Written for its own bundled browser SPA. Endpoints like POST /api/probe, POST /api/estimate, and GET /api/render/{id}/events have no runtime capability handshake for strangers—the embedded vanilla JS frontend already hardcoded every route and payload shape at compile time.
  • ytmix mcp (JSON-RPC 2.0 stdio): Written for any compliant MCP Host (IDE, desktop client, agent harness). Before calling anything, the Host negotiates protocol version and discovers Tools, Resources, and Prompts dynamically at runtime.
Figure 1: All three interfaces wrap the same FFmpeg/FFprobe core, but only ytmix mcp standardizes runtime capability discovery and separates model, host, and user control.

2. Where the Value Lies: Three Distinct Control Models

An HTTP API gives you endpoints—usually GET and POST—and leaves every AI client to invent how to discover schemas, inject read-only context, ask humans for approval, and kick off workflows. The MCP Architecture splits server capabilities into three primitives with different owners, and ytmix/internal/mcp/ uses all three:

MCP Primitive Who Triggers It? Why a REST Endpoint Isn't Enough Concrete Example in ytmix
Tools (tools/call) Model-controlled (Host gates consent) Bundles JSON InputSchema, natural-language selection hints, and behavioral ToolAnnotations (readOnlyHint, destructiveHint) so Hosts know what needs approval. get_capabilities, inspect_tracks, plan_mix (dry-run, zero writes), start_render, verify_mix (9 total).
Resources (resources/read) Application / Host-controlled Exposes read-only URI-addressed data ("nouns") that the Host or user can attach directly to context without burning a model tool-call turn. ytmix://presets, ytmix://themes, ytmix://resolutions, plus live ytmix://jobs/{id} snapshots.
Prompts (prompts/get) User-controlled (slash command / menu) Ships server-authored, multi-step workflow recipes from the tool author so users don't have to memorize safe tool ordering. create-sleep-mix and clean-youtube-release (enforce dry-run plan_mix + user confirmation before start_render).

Why That Matters in Practice: The M×N Problem & Dry-Run Safety

Without MCP (Anthropic MCP Introduction), connecting M AI apps (Antigravity, Claude Desktop, Cursor, custom CI agents) to N tools like ytmix requires M×N custom wrappers—or teaching every client your bespoke REST endpoints (/api/estimate, /api/probe). With ytmix mcp:

  1. Zero-config Host integration: Any MCP Host runs initialize (negotiating 2025-06-18 in registry.go), sends notifications/initialized, and immediately receives typed schemas and descriptions for all 9 tools.
  2. Workflow safety baked into the server: In ytmix, plan_mix carries ReadOnlyHint: true and computes Rendering Path trade-offs (e.g., Path A stream-copy vs. Path B re-encode) plus YouTube Chapter Timestamps with zero disk writes—while clean-youtube-release instructs the model to confirm cleaned displayTitle overrides with you before calling start_render.
  3. Structured + text dual returns: JSONToolResult returns both human-readable JSON text and machine-typed structuredContent, so Hosts can render or inspect outputs cleanly.

Reference 0001 · Quick Lookup

MCP JSON-RPC 2.0 handshake and ytmix primitive map.

1. Host → Server: initialize (protocolVersion: "2025-06-18")
2. Server → Host: capabilities { tools, resources, prompts }
3. Host → Server: notifications/initialized (no id)
4. Runtime:
   • tools/list     → 9 ytmix actions (Model-controlled)
   • resources/read → ytmix://presets|themes|resolutions|jobs/{id} (Host)
   • prompts/get    → create-sleep-mix | clean-youtube-release (User)

Rule of Thumb: REST APIs optimize for build-time known callers; MCP optimizes for runtime-discovering AI Hosts.
